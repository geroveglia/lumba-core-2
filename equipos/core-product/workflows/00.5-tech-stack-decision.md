# Workflow 0.5: Tech Stack Decision (ADR de Arquitectura)

> **Se ejecuta entre Workflow 0 (DB Design) y Workflow 1 (Discovery).**
> **Define el stack técnico completo ANTES de escribir una línea de código.**

---

## Principio

> **La base de datos es el cimiento. El stack es la estructura. Sin ambos definidos, no se construye.**

---

## Cuándo se usa

- **Obligatorio** después del Workflow 0 (DB Design) para todo proyecto de producto digital.
- Cuando un proyecto existente migra de stack.
- Cuando se evalúa una tecnología nueva para un cliente.

---

## Pasos

```
1. frontend-architect → propuesta de stack frontend
   ├── Framework: React / Next.js / Astro / Vue
   ├── Estilos: Tailwind / CSS Modules / Styled Components
   ├── Estado: Context / Zustand / Redux
   └── Justificación basada en tipo de proyecto

2. backend-architect → propuesta de stack backend
   ├── Runtime: Node / Python / Go
   ├── Framework: NestJS / Express / FastAPI / Hono
   ├── Auth: Supabase Auth / NextAuth / Clerk / Custom JWT
   └── APIs: REST / GraphQL / tRPC

3. data-architect → confirma decisión de DB (del Workflow 0)
   ├── Relacional: PostgreSQL (Supabase) / MySQL / PlanetScale
   ├── No relacional: MongoDB / Firebase / DynamoDB
   └── ORM: Prisma / Drizzle / TypeORM / raw SQL

4. devops-engineer → propuesta de infraestructura
   ├── Hosting: Vercel / Railway / AWS / Fly.io
   ├── CI/CD: GitHub Actions / Vercel / Railway
   ├── Entornos: dev / staging / prod
   ├── Monitoring: Sentry / Logtail / Grafana
   └── Variables de entorno: estrategia de secrets

5. backend-architect + frontend-architect → consolidación
   └── ADR: Architecture Decision Record con el stack completo

6. devils-advocate → challenge al stack
   ├── ¿Stack A es realmente el correcto o estamos defaulting?
   ├── ¿Hay overengineering para el tamaño del proyecto?
   ├── ¿El equipo del cliente puede mantener esto?
   ├── ¿Costo de infraestructura mensual estimado?
   └── ¿Lock-in con algún proveedor?

7. product-auditor → auditoría del ADR (Software Gate)
8. PM o socio → aprobación del stack
```

---

## Stacks pre-definidos

Lumba Core tiene stacks tipificados (ver `shared/infra/STACKS.md`):

| Stack | Frontend | Backend | DB | Hosting | Para qué |
|---|---|---|---|---|---|
| **A** (default) | Vite + React + TS + Tailwind | NestJS (si necesita) | Supabase (PostgreSQL) | Vercel + Supabase | 80% de proyectos |
| **B** | Next.js + TS + Tailwind | Next.js API routes | Supabase (PostgreSQL) | Vercel + Supabase | 15% — necesita SSR/SEO |
| **C** | React + TS + Tailwind | NestJS + microservicios | PostgreSQL + Redis | AWS ECS / K8s | 5% — enterprise |
| **Legacy** | jQuery / Vanilla | PHP / Laravel | MySQL | cPanel / VPS | Solo mantenimiento |

**Regla:** si el proyecto calza en Stack A → Stack A. No overengineerear.

## Output

- **ADR de Stack Decision** (`/proyectos/{nombre}/outputs/00-adr-stack.md`):
  - Stack elegido y justificación.
  - Alternativas consideradas y descartadas.
  - Costo mensual estimado de infraestructura.
  - Plan de entornos (dev/staging/prod).
  - Estrategia de CI/CD.
  - Variables de entorno necesarias (nombres, no valores).

---

## Quality Gate

- **Architecture Gate** — el ADR debe pasar auditoría del Devil's Advocate antes de avanzar.
- Si el stack no es el correcto → iterar.
- Máximo 2 iteraciones antes de escalar al Founder.

---

## Duración estimada

1-3 días.

---

## Validación humana

- Tech Lead o Founder aprueba el stack.
- Si el cliente tiene preferencias técnicas, se incorporan como restricción en el brief.

---

## Anti-patterns

- ❌ "Usemos Stack A siempre sin pensar."
- ❌ "Elijamos la tecnología más nueva porque está de moda."
- ❌ "No necesitamos entornos separados, deployemos directo a prod."
- ❌ "El stack lo decidimos sobre la marcha."
- ❌ "No documentemos las alternativas descartadas."
